# Go-live checklist — providers that are built and waiting for keys

Everything below is coded and tested with mocks. Each one switches on when its secrets are set on
the Cloudflare Workers (`wrangler secret put NAME` for each Worker listed). Nothing else changes.
Check status any time in **ops.guma.one → Settings → Integrations** (shows configured / missing).

Never paste secret values into chat, docs or commits.

## 1. SMS — Semaphore (buyer updates, reminders, seller alerts, POS receipts, SMS campaigns)

| Secret | Workers | Notes |
|---|---|---|
| `SEMAPHORE_API_KEY` | admin, web | From semaphore.co → Account → API (also turns on Guma ID sign-in, section 6) |
| `SEMAPHORE_SENDER_NAME` | admin, web | Optional. Your approved sender name (e.g. `GUMAKART`). Without it Semaphore uses its default |
| `SMS_OPT_OUT_SECRET` | admin, web | Already generated by `scripts/deploy-cloudflare.ps1`; must be the same on both |

Before: texts are logged as **"Not sent"** in Automate → Auto SMS and ops → SMS & opt-outs.
After: send one test order to your own phone; check Auto SMS shows **Sent**.

## 2. Email — Resend (signup codes, password resets)

| Secret | Workers | Notes |
|---|---|---|
| `RESEND_API_KEY` | admin, web, platform | resend.com → API keys |
| `EMAIL_FROM` | admin, web, platform | e.g. `Guma Kart <no-reply@guma.one>` — domain must be verified in Resend (DNS records in Cloudflare) |

Before: production refuses to send codes ("We couldn't send the email right now").

## 3. Online payments — PayMongo (GCash / Maya / QR Ph / card through PayMongo)

Waiting on: Guma One business + BIR registration, then PayMongo account activation.

| Secret | Workers | Notes |
|---|---|---|
| `PAYMONGO_SECRET_KEY` | web, admin | Live `sk_live_…` |
| `NEXT_PUBLIC_PAYMONGO_PUBLIC_KEY` | web | Live `pk_live_…` (build-time variable) |
| `PAYMONGO_WEBHOOK_SECRET` | web | From the webhook you create for `https://kart.guma.one/api/webhooks/paymongo` (events: `payment.paid`, `payment.failed`, `checkout_session.payment.paid`) |

Then per shop: ops → Tenants → shop → Payments mode → `paymongo` or `both`.
Until then sellers use **direct GCash/Maya** (buyer uploads proof, seller confirms) and COD — fully working.
Test: ₱1 per method (GCash, Maya, QR Ph, card) on a test shop, confirm the order turns Paid by itself.

## 4. Messenger & Instagram — Meta (Phase 13, built, ready to hook up)

Waiting on: Meta business verification + app review for `pages_messaging`, `pages_manage_metadata`,
`pages_show_list`, `instagram_basic`, `instagram_manage_messages`. Do not submit documents that
aren't real; use the actual Guma One registration papers.

| Secret | Workers | Notes |
|---|---|---|
| `META_APP_ID` | admin | Meta app id |
| `META_APP_SECRET` | admin | Checks webhook signatures and exchanges login codes |
| `META_VERIFY_TOKEN` | admin | Any random string; paste the same into the Meta webhook setup |
| `CHANNEL_TOKEN_KEY` | admin | Optional, 32+ random characters; seals Page/marketplace tokens (falls back to `AUTH_SECRET`) |

In the Meta app: Facebook Login redirect `https://admin.guma.one/api/channels/meta/callback`;
Webhooks (Page + Instagram) callback `https://admin.guma.one/api/webhooks/meta`, fields
`messages`, `messaging_postbacks`, `message_echoes`. Test: connect a test Page from Channels, send
it a message from another account, reply from Chats, send a product card, order from it — the
order shows in the chat and under Messenger in Channels. Replies only within 24 h of the buyer's
last message (Meta's rule).

## 4b. Shopee & Lazada (Phase 13, built, ready to hook up)

| Secret | Workers | Notes |
|---|---|---|
| `SHOPEE_PARTNER_ID`, `SHOPEE_PARTNER_KEY` | admin | Shopee Open Platform live partner app (`SHOPEE_API_HOST` optional for the sandbox) |
| `LAZADA_APP_KEY`, `LAZADA_APP_SECRET` | admin | Lazada Open Platform app (`LAZADA_API_HOST` optional; default PH) |

Redirect URLs: `https://admin.guma.one/api/channels/marketplaces/shopee/callback` and
`.../lazada/callback`. The admin cron pushes stock and imports paid orders every 5 minutes.
First real sync: watch one shop — check listings auto-linked by SKU, one stock push, one imported
order, one cancellation (restocks). Endpoint fields follow the 2026 public docs; adjust if the
partner console differs.

## 4c. Email copies of order updates (Phase 13)

Uses the Resend setup in §2. Buyers who type an email get order received / paid / shipped / out
for delivery / delivered emails; the POS can email a receipt. Shops can turn it off in Auto SMS.
`EMAIL_FROM` must be on the verified domain.

## 5. BIR sales invoices for POS (built, off by default — Phase 11)

Each shop turns it on in Settings → POS → "BIR sales invoices" after entering its PTU details
(registered name, TIN, address, MIN, serial, PTU no.). Do this only after an accountant/RDO
confirms the sales-invoice format, numbering series and X/Z reading layout. Until then receipts
say "This is not an official receipt". Guma Kart is not a BIR-accredited POS provider.

## 6. Guma ID — buyer sign-in by text code (Phase 12)

| Secret | Workers | Notes |
|---|---|---|
| `GUMA_ID_SECRET` | web | 32+ random characters (`openssl rand -base64 48`). Signs buyer sessions and keys the code hashes. Falls back to `AUTH_SECRET` if set on web |

Needs **Semaphore** (section 1) — the code is sent by SMS. Until both are set, Guma ID shows
"Malapit na" and checkout works as before. After: open kart.guma.one/account, sign in with your
own number, place a test order from a checkout link and check it appears under "Mga order".

## 7. Public API & webhooks (Phase 15 — no new secrets)

Works as soon as migration 0033 is on Neon. Webhook signing secrets are sealed with
`CHANNEL_TOKEN_KEY` (else `AUTH_SECRET`) — rotating that key makes stored webhook secrets unreadable,
so shops would rotate their webhook secrets. Optional: `UPSTASH_REDIS_REST_URL` /
`UPSTASH_REDIS_REST_TOKEN` (admin) make the API rate limit hold across Worker instances.
