# Phase 4 — Automatic SMS

Plan: `docs/GUMA-KART-V1-PLAN-REVISED.md` (SMS automations). No migration — uses the Phase 2 tables
(`domain_events`, `message_log`, `messaging_opt_outs`, `checkout_sessions`).

## How it runs

| Piece | Where | When |
|---|---|---|
| Order-event recipes | `apps/admin/lib/automations.ts` → `handleOrderEvent`, called by the outbox relay `/api/cron/outbox` for every event before it's marked published | every 5 min (cron tick) |
| Timed recipes | `runTimedAutomations` via `/api/cron/automations` (new entry in `cron-worker.ts`) | every 5 min |
| Texts | `packages/services/src/messaging/recipes.ts` (pure, unit-tested) | — |
| Candidates / claims | `packages/db/src/queries/automations.ts` | — |

- **Once only:** every text goes through `sendWithLog` with key `recipe:entity:step`. A replayed event or
  overlapping cron run can't text twice; unfinished-checkout steps are also claimed compare-and-set.
- Events older than 24 h are not texted (no "your order shipped" a day late after an outage).
- Inngest stays optional: when configured, events are still forwarded after the built-in recipes run.

## Recipes (buyer)

All start with the shop name, Taglish, ASCII only (`P1,890`, not `₱`) so one SMS = 160 chars.

| # | Recipe id | Trigger | Kind |
|---|---|---|---|
| 1 | `order_created` | at checkout (place-order) — wording now depends on COD / pickup / e-wallet | transactional |
| 2 | `payment_confirmed` | `Order.PaymentConfirmed` (not COD) | transactional |
| 3 | `shipped` | `Fulfillment.Booked` (delivery) or `Fulfillment.Ready` (pickup, with address + cash due) | transactional |
| 4 | `out_for_delivery` | `Fulfillment.OutForDelivery`, with "Pakihanda ang P… cash" when COD is due | transactional |
| 5 | `delivered` | `Fulfillment.Delivered` | transactional |
| 6 | `abandoned_checkout` | 30 min (cart < 12 h old) and 24 h (cart < 72 h old); max 2; link carts go back to the link only while it's live | marketing |
| 7 | `unpaid_reminder` | e-wallet/online order unpaid 6 h after ordering (< 48 h), once | marketing |

Marketing = buyer ticked "text me reminders" (session consent / `customers.sms_marketing_opt_in`),
"Stop reminders" link (`withOptOutFooter`, enforced by `sendWithLog`), never 9 PM–8 AM Manila. If the
opt-out secret is missing, reminders are skipped and nothing is claimed. Buyer texts stop if the order
was cancelled. Seller can switch each recipe off (`settings_json.automations.<id> = false`; missing = on).

## Seller alerts

- Push (when the seller allowed notifications): payment proof sent, delivery failed. New COD orders were
  already pushed at checkout; e-wallet orders now push "New order — waiting for GCash payment" instead of
  the wrong "New COD order".
- SMS (opt-in, "Text me too" on Auto SMS = `notifications.smsOnNewOrder`): new COD order, payment proof,
  delivery failed. Goes to Business → mobile, else the WhatsApp number, else the owner's phone.

## Seller UI — Automate → Auto SMS (`/automations`)

30-day numbers (texts sent, recovered checkouts + sales, not sent), on/off per recipe with a sample
text, "Text me too", and the last 50 texts (number masked, status: Sent / Not sent / Buyer opted out /
Test only). Banner when `SEMAPHORE_API_KEY` isn't set.

## Tests

- `packages/services/src/messaging/recipes.test.ts` (9): ASCII, shop prefix, COD wording, quiet hours, toggles.
- `packages/db/src/automations.test.ts` (4, integration): candidate rules (consent, phone, timing,
  ordered-since by any phone format), claim once, link cart closed → no text, unpaid reminder once.
- Manual (local): seller confirm → ready → out for delivery → delivered sent 3 buyer texts; pickup ready
  text with address + cash; a consented 45-min-old link session got the step-1 text with the stop link,
  and the next run sent nothing.

## Deploy

No migration. Needs `SEMAPHORE_API_KEY` (and `SMS_OPT_OUT_SECRET`, already generated by the deploy
script) on **both** admin and web Workers. Without the key, texts are logged as "Not sent".
